# AI Feedback: архитектура проекта RestAssured-Demo

## Обзор текущего состояния

- **Стек:** Java 25, Gradle, JUnit 5 (Jupiter), RestAssured 6.0.1, Jackson (databind), Hamcrest.
- **Структура:** весь тестовый код лежит в `src/test/java/homework17/` и состоит из **4 файлов**:
  - `ServeRestTest.java` — основной набор тестов на пользователей/товары (через кросс-тестовое состояние);
  - `ProdutosCarrinhoTest.java` — самодостаточные тесты на товары и корзину (добавлены нами);
  - `Usuario.java`, `Produto.java` — простые DTO без Lombok (комментарий «Lombok не захотел взлетать»).
- Часть test-run логов перенесена в `test-output/` и скрыта через `.gitignore`.

---

## Что сделано хорошо

1. **Глобальная конфигурация через `@BeforeAll`** — `baseURI` и логирование при валидации вынесены в `setup()`; тесты компактны, не дублируют base URL.
2. **DTO вместо сырых JSON-строк** в части мест (`new Usuario(...)`, `new Produto(...)`) — типобезопасность, автодополнение в IDE, переиспользование.
3. **Правильное использование хелперов** — `enableLoggingOfRequestAndResponseIfValidationFails()` упрощает отладку при падении.
4. **Стремление к самодостаточности тестов** (в `ProdutosCarrinhoTest`, в рефакторинге `shouldUpdateUserSelfContained`) — это заметный шаг к устойчивым автотестам.
5. **`.gitignore`** корректно скрывает `build/`, `.gradle/` и логи запусков.

## Ключевые проблемы и риски

### 1. Кросс-тестовое состояние через `static` поля (самая серьёзная проблема)
В `ServeRestTest` данные пробрасываются между тестами через `static userId`, `token`, `email`. Тесты **упорядочены** `@Order(...)` и жёстко зависят друг от друга:
- `shouldUpdateUser` (исходный) использует `userId` из создания,
- `shouldLogin` использует `email` из создания,
- `shouldDeleteUser` использует `userId` + `token` из двух предыдущих.

**Риски:** любой тест нельзя запустить в одиночку; случайный порядок/параллельность ломает всё; если один шаг упадёт — «каскад» ложных падений в следующих. Это делает тесты хрупкими и трудными для диагностики.

> Рекомендация: изолировать каждый тест (создавать свои данные внутри теста), как уже сделано в `shouldUpdateUserSelfContained`.

### 2. Смешение проверок и десериализации в одном месте
В `shouldUpdateUserSelfContained` я оставил проверки через Hamcrest (это нормально). Но в целом страдает читаемость: тело JSON «инлайн» в тесте. Путь «тело в отдельном методе» (`asUpdatePayload`) верный — стремиться к этому повсеместно.

### 3. Неполнота проверок (что уже частично закрыто)
Ранее `shouldUpdateUser` проверял только `message`. Мы добавили верификацию через `GET` после обновления — рекомендую такой же паттерн применять и к другим CRUD-тестам.

### 4. Кодировка исходников
Проект компилируется без `-encoding UTF-8` (`build.gradle`), из-за чего не-ASCII символы в `.java` читаются как кракозябры. Мы из-за этого ушли на `\u00ed`, `\u00e3`, ASCII-имена в ассертах. 

> Рекомендация: добавить `tasks.withType(JavaCompile) { options.encoding = 'UTF-8' }` — это устранит целый класс «магических» падений.

### 5. Отсутствие слоя «конфигурация/утилиты»
`baseURI`, данные входа (`secret123`), логика авторизации дублируются в обоих тест-классах. Нет общего модуля (например, `TestConfig`, `AuthProvider`, `CartBuilder`). При росте это приведёт к дублированию.

> Рекомендация: при расширении проекта выделить общие хелперы (создание админа, логин, уникальные email).

### 6. Жёстко заданные ожидаемые сообщения/коды
Ассерты на португальские сообщения хардкодятся. Это ок для учебного API, но на реальном SUT хрупко. Можно убрать чрезмерную привязку к тексту, оставив проверку кодов и ключевых полей.

## Общий вердикт

Для **учебного** проекта архитектура более чем рабочая и уже показывает осознанные паттерны (DTO, самодостаточные тесты в одном из классов). Главная рекомендация на следующий шаг — **уйти от зависимостей между тестами через `static`**, добавить UTF-8 в `build.gradle` и при необходимости вынести общую логику в утилиты. С этими изменениями проект готов «дорасти» до настоящего тестового фреймворка.
